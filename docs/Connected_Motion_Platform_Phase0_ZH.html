背景与职业目标

这是独立的个人工程项目，灵感来自 Aiving Jump Tracker，不复制其专有算法或内部架构。目标是构建数据采集、MQTT、后端、数据库、API、监控及分析的端到端平台，用作 Senior Software Engineer、Systems Engineer、IoT Engineer 和 Software Architect 的作品。

已有四年以上 C#/.NET、REST API、Azure、Unity、BLE、实时系统、软硬件集成、CI/CD 与测试经验。在 Alsensia 参与可穿戴传感器与 VR 集成，并带领另一位工程师。项目以 .NET 为核心；Python 用于模拟及分析，逐步补齐其工程实践。

约束与方法

目前没有 Sensor、ESP32 或 IMU。第一版全软件模拟，优先 Windows，完整 MVP 可在本地运行且不依赖付费云。优先开源工具与模块化设计，暂不引入复杂微服务或 Kubernetes。每阶段解释原理、实现、运行、测试、故障分析并验收后，再进入下一阶段。

2 系统架构与模块职责

采用模块化单体后端：ASP.NET Core 同时承载 REST API 与 MQTT BackgroundService。接收和查询隔离职责，第一版保持一个部署单元；当采集负载干扰查询或需要独立扩容时，再考虑拆分。

数据路径

职责

Simulator → Mosquitto

生成可复现信号，发布 telemetry 和 status

Mosquitto → MQTT Adapter

订阅、路由并传递 Topic 与 MQTT 元数据

Adapter → 有界队列 → Processor

解耦接收与写入，验证、去重、受控背压

Processor → PostgreSQL

事务保存、唯一约束与迁移

REST API → Query → PostgreSQL

设备及历史数据查询，限定范围并分页

Backend → Prometheus → Grafana

吞吐、延迟、错误率和队列深度

未来 IMU → BLE Gateway → MQTT

转换坐标与单位，适配契约

模拟器不实现 BLE/GATT。未来硬件替换数据源时，后端沿用契约，但配对、分包、网关重连及安全需要另行设计和验证。

有界队列与持久化

队列吸收短时波动，但容量必须受限。满载时采用明确等待或受控拒绝策略，并结合 MQTT 确认行为验证。内存队列没有持久化保证。回调结束、Broker 确认、数据库提交是不同事件；不能以 QoS 1 宣称端到端零丢失。

Windows 开发部署

Python 和 .NET 初期在 Windows 本机运行，便于调试；Mosquitto、PostgreSQL 和后续监控通过 Docker 运行。本机用 localhost，容器间用 Compose 服务名。Phase 3 加入应用容器。Broker 端口仅绑定回环地址，显式认证，凭据不提交 Git。Docker 环境及适用条件在 Phase 1 核实。

4 MQTT 消息契约

Topic

QoS 与 Retain

motion/v1/devices/{deviceId}/telemetry

QoS 1；Retain false

motion/v1/devices/{deviceId}/status

QoS 1；Retain true

后端订阅 motion/v1/devices/+/telemetry 和 motion/v1/devices/+/status。Topic 标识设备和消息类型，不按轴拆分，不放时间戳或 Message ID。

{
  "schemaVersion": 1,
  "messageId": "50aec828-b1a6-45d7-8d9a-e48b3e51ea75",
  "deviceId": "sim-001",
  "streamId": "a6e91f23-4bbc-49c0-a438-ea8f092a3b88",
  "sequence": 42,
  "sampledAt": "2026-10-22T08:00:00.123Z",
  "accelerationMps2": {
    "x": 0.03,
    "y": -0.02,
    "z": 9.81
  },
  "angularVelocityRadps": {
    "x": 0.001,
    "y": -0.002,
    "z": 0.0
  },
  "simulation": {
    "scenario": "idle"
  }
}

每条一个采样点。messageId 标识样本；streamId 标识采样流；sequence 从 0 递增。重试保留原 ID、序列和采样时间；进程重启生成新 streamId，单纯重连可以保持。streamId 不是训练会话 ID。

加速度 m/s²，包含重力；角速度 rad/s。设备局部右手坐标：X 前、Y 左、Z 上，旋转遵循右手定则；静止且 Z 向上约为 (0, 0, 9.81)。Gateway 统一转换，Unity 显式映射。

sampledAt 是 UTC 采样时间，后端另记 receivedAt。二者之差含时钟误差，不能未经同步就视为网络延迟。验证字段、版本、UUID、Topic 身份一致、非负序列、UTC 和有限数值；未知可选字段可忽略。格式错误与物理异常分开处理。simulation 是参考标签，不能作为检测输入或检测成功证据。

5 设备状态 数据存储与 API

{
  "schemaVersion": 1,
  "deviceId": "sim-001",
  "connectionId": "1772e900-cc6f-433d-9ca9-d897f233030b",
  "state": "online",
  "reportedAt": "2026-10-22T08:00:00.000Z",
  "batteryPercent": 100
}

连接前注册 retained offline 遗嘱；连接后发 retained online 并定期心跳；正常退出主动发 offline。遗嘱不能预知实际断线时间，其 reportedAt 允许 null，后端另记观察时间。每次连接生成新 connectionId。保留状态可能过时，API 区分报告状态与依据最后消息时间推导的活跃状态。电量限定 0 至 100。

模型

字段与约束

devices

device_id 主键；first_seen_at；last_telemetry_received_at；last_status_received_at；reported_connection_state；battery_percent

sensor_readings

message_id 主键；device_id；stream_id；sequence；sampled_at；received_at；加速度及角速度三轴

唯一与索引

device_id + stream_id + sequence 唯一；device_id + sampled_at + message_id 查询索引

冲突处理

同身份不同内容记录冲突，不覆盖原样本

GET /api/v1/devices
GET /api/v1/devices/{deviceId}
GET /api/v1/devices/{deviceId}/readings
    ?from=...&to=...&limit=...&cursor=...
GET /health/live
GET /health/ready

限制历史查询时间范围和条数；live 说明进程可响应，ready 说明关键依赖和接收链路就绪。依赖故障不必然通过重启修复。Python/paho-mqtt、.NET/MQTTnet/ASP.NET Core、PostgreSQL、Compose、Prometheus/Grafana、xUnit/pytest/GitHub Actions 和后续 pandas 的具体版本在各阶段实施时核实并锁定。

6 故障语义 可靠性与扩展

情况

设计行为与边界

重复

数据库唯一约束去重并计数

乱序和缺口

接受合法迟到样本；缺口先记为待核实

非法消息

拒绝并计数，日志避免无限重复刷屏

Broker 故障

自动重连；初期不保证完整补传断线期间数据

数据库故障

有界重试、背压和 ready 异常

后端退出

内存未提交数据存在丢失窗口

Phase 4 再通过实验决定磁盘缓冲、应用层确认、持久会话或其他恢复机制。必须区分 MQTT 协议投递与业务入库，恢复连接不等于数据完整，QoS 1 不等于 exactly once 持久化。

设备数量增加一百倍

先估算设备数 × 采样率 × 消息大小；测量吞吐、P95/P99 处理耗时、CPU、内存、队列和数据库速率。按真实瓶颈考虑批量消息与写入、保留策略和分区、独立采集进程、并行消费及分区内顺序，不凭设备数直接选择微服务。

负载报告记录机器配置、软件版本、采样率、持续时间、数据量、故障注入、重复和丢失定义及优化前后结果。100 至 1000 台设备是实验目标，尚非能力声明。

数据分析边界

Phase 5 以 Python/pandas 清洗缺失、异常和重复，计算特征、规则事件及趋势，并保留原始数据溯源。事件识别仅为工程示例，不能宣称真实花样滑冰识别准确率。标签与观测的隔离方法见后文专页。

9 观测数据 场景标签与检测结果

模拟器知道自己安排了什么场景；后端算法必须根据传感器信号独立判断发生了什么。前者是参考，后者是待验证结果。

层次

内容与用途

观测 Observations

加速度、角速度、时间、设备 ID；供检测器输入。

标签 Reference labels

模拟器生成的 jump 区间；只用于调试、评估和有条件的监督训练。

结果 Predictions

检测器独立输出事件类型、时间区间、规则版本；再与参考标签匹配。

错误和正确做法

# Incorrect: copies the answer rather than detecting an event
if message["simulation"]["scenario"] == "jump":
    emit_event("jump")
# Correct boundary: detector receives observations only
observations = project_sensor_fields(message)
predictions = detector.detect(window(observations))
evaluation = compare(predictions, reference_intervals)

例：模拟器把 10.0 至 10.8 秒设为 jump。检测器只能看到时间窗里的加速度和角速度，并独立输出 10.1 至 10.7 秒的候选事件。评估器再匹配区间。若落地的一次峰值被误认成跳跃，应算误报，不能靠读取标签修正输出。

第一版如何保持简单

Phase 1 为便于调试，消息可保留可选 simulation 字段，但检测入口使用独立类型且显式投影观测字段。Phase 5 将参考区间保存到独立数据集并在检测后关联；不要求现在增加新的 MQTT 服务。设备 ID、streamId 或命名规则也不能隐式编码答案。

验证方法与结论边界

固定观测数据，删除、打乱或改名标签，预测必须保持不变；改变输入信号时输出才可能改变。规则阈值只在开发集调优，按采样流或独立种子划分留出集，避免重叠时间窗跨集合。评估事件级 precision、recall 和时间误差；先定义一对一匹配和容差。合成场景标签可能与波形不完全一致，需检查生成器。合成评估通过也不能证明真实硬件或真实跳跃准确率。
