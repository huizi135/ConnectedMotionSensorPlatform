已验证与本步目标

用户 Windows 已通过 Broker 基础 smoke test、五项 idle 信号测试及三个离线样本。三个样本 sequence=0,1,2，UTC 时间相差 0.1 秒，加速度 Z 约为 9.81。现在验证 Windows Python 发布 → Docker Broker → 独立 Windows Python 订阅。助手环境十三项测试通过；用户 Windows 单发布端/单订阅端十条样本真实 MQTT 验收已通过，消息 ID 与序号逐一对应。

烘焙类比与真实流程

生成器是虚拟烤箱探头；发布端是送报告的人；Broker 是消息调度台；订阅验证端是读取报告的记录员。先让记录员登记接收频道，看到 READY 后再送十份报告。每份都要检查格式与编号。记录员目前只在内存中核验，没有写入正式数据库。

CONNACK 确认连接结果；SUBACK 确认订阅结果；QoS 1 PUBACK 确认 Broker 对发布的响应。收到确认还要检查 reason code；收到成功 PUBACK 不代表另一个客户端已接收，更不代表数据库提交。最后必须检查订阅端自己的结果。

步骤 1：安装项目依赖并测试

git pull --ff-only
.\.venv\Scripts\python.exe -m pip install -r simulator/requirements-mqtt.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v

新增 paho-mqtt 固定版本 2.1.0；复用已有 jsonschema 契约依赖，不需全局安装。预期十三项测试通过。Paho 是 Python MQTT 客户端，不是 Broker。

步骤 2：确认 Broker，启动订阅端

docker compose -f infrastructure/compose.yaml up -d mosquitto
.\.venv\Scripts\python.exe -m simulator.mqtt_demo subscribe --samples 10

在窗口 A、仓库根目录执行。看到 READY: subscription accepted 后，程序会等待，默认最长 120 秒。这不是卡住：记录员正在等报告。若超时，重新运行订阅端，并在 READY 后启动发布端。

步骤 3：第二个窗口发布

Set-Location "C:\Users\Admin\Documents\GitHub\ConnectedMotionSensorPlatform"
.\.venv\Scripts\python.exe -m simulator.mqtt_demo publish --samples 10

窗口 B 使用相同虚拟环境和设备 ID。预期 sequence=0..9 的十条 ACK 和 PASS publisher。窗口 A 收到十条合法、唯一、连续的 JSON，打印 PASS subscriber，然后退出。两端都成功才通过本步验收。不要同时启动多个发布端或复用该频道做其他测试。

采样时间与发送节奏

复用 idle_samples，计划每 0.1 秒发布一个逻辑样本，用 monotonic 时钟安排目标时间，UTC 表示采样时间。每条等待成功 PUBACK，最多等待十秒。桌面调度、网络延迟可能让发布落后；落后后可能追赶，实际节奏不是硬实时，也不保证严格 10 Hz。当前只做十条小批量功能验收，负载控制和慢链路策略后续设计。

职责和恢复边界

部分职责
signals.py无网络的确定性生成核心。
mqtt_demo.py Connection单线程网络循环，直接处理连接、订阅、发布 reason code。
publish校验 JSON、QoS 1、retain=False，等待 Broker 确认。
subscribe校验 Topic 与正文，按身份去重、冲突检测，核验本次演示序号。

本步使用临时干净会话，没有自动重连、磁盘缓冲和断线补发；连接丢失会报错退出。订阅端要求单流从序号 0 开始，缺号/乱序报错用于发现演示异常，不是未来后端拒绝乱序的业务规则。重复相同内容不增加计数，冲突重复报错。收齐后状态消失，不是持久幂等。

常见故障

  • 找不到 paho：确认执行了项目 .venv 下的 pip 安装命令。
  • Connection refused：确认 Docker Desktop 和 Broker 已启动，端口仍为本机 1883。
  • Not authorized：保留错误，不放开匿名、不删除凭据；检查是否使用当前项目凭据。
  • Receive samples timed out：确认先订阅并看到 READY；两端样本数和 device-id 相同，发布端在 120 秒内启动。
  • 序号从非零开始或多个流：检查是否先运行了发布端，或同一频道还有其他发布程序。重新按顺序运行即可，不需要删除卷。

面试问题与参考答案

问：为什么还需要独立订阅端？ 发布成功只能说明 Broker 侧确认；独立接收验证了路由、权限和实际消费者收到合法内容。本步补齐了此前容器内客户端测试没有覆盖的 Windows Python 路径。

问：为什么不直接检查 publish() 返回值？ 返回成功可能只表示进入本地发送队列。QoS 1 还需等待 PUBACK 并检查 reason code；即使成功，也不能代表数据库落盘。

问：如何避免回调与主线程竞态？ 当前用单线程手动 network loop，在同一执行线程处理回调。之后引入后台线程时应显式设计共享状态与同步，不能假定接口调用顺序等于网络事件顺序。

问：断线会怎么样？ 当前演示失败退出，不承诺回放。后续分别设计重连退避、缓存容量、身份保留、确认边界和故障验收，再提升保证。
