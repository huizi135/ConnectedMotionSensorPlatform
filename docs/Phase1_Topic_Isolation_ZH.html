Phase 1 小步实践：两个设备频道会不会串线？

2026-10-23 · 本页是阶段内操作手册，非 Phase 1 完成报告。

本次通过了什么？

Windows 发布端收到十个成功 PUBACK；独立订阅端收到 sequence 0–9，messageId 与发布端逐一一致，全部契约校验通过。同一 streamId 34c9cbc4-beef-436b-9729-0f5d4d02c9a0 的采样时间从 14:10:50.669281Z 到 14:10:51.569281Z。

这证明本次单设备正常运行链路通过。订阅端会去重，因此十个唯一消息不代表线上绝无重复；也不能由采样时间差推断传输延迟。尚未验证数据库、崩溃恢复或多设备容量。

为什么验证两个频道？烘焙类比

工作室现在有烤箱 001 和烤箱 002，各有一个报告频道。记录员 A 只登记 001，记录员 B 只登记 002。我们先发送 001 的报告，检查 B 是否仍在等待，再发送 002 的报告。目的是检查分类与分发是否串线，不是测试厨房大规模产能。

设备实际 Topic接收者
sim-live-001motion/v1/devices/sim-live-001/telemetry窗口 A
sim-live-002motion/v1/devices/sim-live-002/telemetry窗口 B

这里只验证 Topic 路由隔离。两台设备仍共享 simulator 账号，ACL 允许它发布多个设备频道，因此不构成设备身份的安全隔离。

步骤 1：更新文档

Set-Location "C:\Users\Admin\Documents\GitHub\ConnectedMotionSensorPlatform"
git pull --ff-only

本步没有新增依赖和应用代码，不需要重装、不需要重置密码。保持 Docker Desktop 和 Broker 运行。

步骤 2：窗口 A 登记设备 001

.\.venv\Scripts\python.exe -m simulator.mqtt_demo subscribe --device-id sim-live-001 --samples 10 --timeout 300

看到 READY 后保留窗口。--device-id 决定要接收的频道，--samples 是等待的唯一样本数，--timeout 300 给手动切换窗口留五分钟。

步骤 3：窗口 B 登记设备 002

Set-Location "C:\Users\Admin\Documents\GitHub\ConnectedMotionSensorPlatform"
.\.venv\Scripts\python.exe -m simulator.mqtt_demo subscribe --device-id sim-live-002 --samples 10 --timeout 300

另开 PowerShell，在新窗口执行。看到 READY 后，两个记录员都准备好了。

步骤 4：窗口 C 先发送设备 001

Set-Location "C:\Users\Admin\Documents\GitHub\ConnectedMotionSensorPlatform"
.\.venv\Scripts\python.exe -m simulator.mqtt_demo publish --device-id sim-live-001 --samples 10 --seed 42

预期：窗口 C 发布 PASS；窗口 A 收到十条 deviceId=sim-live-001 并 PASS；窗口 B 保持等待，没有 JSON。不要关闭 B，也不要在 A 继续启动其他发布者。

步骤 5：窗口 C 再发送设备 002

.\.venv\Scripts\python.exe -m simulator.mqtt_demo publish --device-id sim-live-002 --samples 10 --seed 84

预期：窗口 C 再次发布 PASS；窗口 B 收到十条 deviceId=sim-live-002，sequence=0..9，并 PASS。seed 84 让两台虚拟探头的噪声更易区分；路由依据是 Topic，不是噪声或 seed。每个新发布进程创建新的采样流。

验收和失败处理

  • A、B 各自只显示目标设备，均收到十条唯一合法样本并通过。
  • C 两次发布均成功。记录 A、B 的结果，以及发送 001 时 B 是否仍在等待。
  • 这是两个订阅端同时连接、两个发布端依次运行的路由检查，不是同时多设备连续发布或负载测试。
  • 超时先检查是否在五分钟内发布、device-id 是否一致。重新启动对应订阅并发布新流即可，不删除卷。
  • 如果出现设备串线、序号错误或拒绝，保留实际输出，停止后续步骤，不通过修改权限掩盖错误。

高级工程与面试问答

问：Topic 中有 deviceId，为什么 Payload 还要有？ Topic 支持 Broker 路由和权限匹配；正文携带业务身份，方便存储、导出和重放。入口必须交叉校验二者一致，避免把数据记到错误设备名下。本项目已有这一校验。

问：频道分开就安全了吗？ 不是。当前共享角色凭据可操作多设备频道。真实设备身份隔离需要独立身份与限制到本设备频道的授权，Topic 命名本身不提供认证。

问：为什么先依次发布？ 用最少变量检查路由，把频道错误与并发调度问题分开。通过后再增加同时发布；不能用本结果宣称大规模并发能力。

问：如何订阅所有设备？ 未来可以订阅 motion/v1/devices/+/telemetry，+ 匹配单个层级。那时接收端必须按 deviceId 和 streamId 分别维护状态；本步程序仅支持单设备精确订阅，暂不把通配符作为 CLI 参数。
