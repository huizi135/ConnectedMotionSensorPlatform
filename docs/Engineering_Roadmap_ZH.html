3. Linux 到底选择什么？

当前继续使用 Windows 开发 + Docker Desktop 的 WSL2 Linux 容器引擎。 没有证据表明安装了用户 Ubuntu 发行版、独立 Linux VM 或独立主机。Docker Desktop 的 WSL2 引擎不要求另装 Ubuntu。

烘焙类比：Windows 是你熟悉的工作台；WSL2 提供 Linux 厨房运行条件；容器是规格明确的设备工作舱。Ubuntu 可以作为额外的 Linux 练习操作间，独立 VM 像另一间完整厨房，独立主机像另租一处店面。当前不需要为一套本地系统同时搭建三种环境。

Linux 学习不能只写“运行过容器”。接下来用实际故障练习 shell、进程与信号、权限、环境变量、DNS/端口、卷、日志和健康检查。需要更完整 shell 练习时，再选装 WSL2 Ubuntu LTS；干净 Linux VM 可作为之后部署验收目标，独立硬件不是前提。

5. 数据库与后端设计意向

保持一个模块化 .NET 后端部署，内部区分 MQTT 适配器、校验/处理、持久化和查询 API。最初 devices 与 sensor_readings 足够；没有多传感器要求时，不额外堆一个没有职责的 Sensor 表。

数据库约束规划：message_id 唯一；(device_id, stream_id, sequence) 唯一；设备外键；UTC 采样时间与接收时间分开；(device_id, sampled_at, message_id) 支持历史查询。重复重试应保持身份，同一身份不同内容要诊断，不能静默覆盖。

数据访问初选 EF Core + Npgsql Provider：EF 管理模型和迁移，Npgsql 连接 PostgreSQL，二者不是二选一。同时实际练习参数化 SELECT、JOIN、INSERT、UPDATE 和事务，不把 ORM 作为不会 SQL 的借口。直接 Npgsql/Dapper 是备选，需要更多映射与迁移维护；吞吐出现实测瓶颈时再评估批量写入或 COPY。

.NET 10 LTS 是实施候选，SDK、EF Core、Npgsql 和 MQTTnet 的兼容版本在 Phase 2 开始时固定。当前没有安装或写出这些功能。查询性能要基于固定数据集与 EXPLAIN (ANALYZE, BUFFERS)；小表顺序扫描可以合理，ANALYZE 会实际执行语句。

6. 为什么当前先做自动状态验收？

烘焙类比：我们已有“开工、下班、突然断电后代挂离线牌”的操作，但还没有一套能重复跑完并核对结果的检查流程。先把这个检查做成按钮，后面接数据库时，故障才更容易归因。

新增 tools/test_status_lifecycle.py，直接使用已有 status_demo：创建独有测试设备、先订阅、启动一秒设备进程，验证正常上下线；随后用进程退出码 17 模拟异常结束，验证 Broker Will；每种情况都再开新订阅读取 retained offline。检查 connectionId 与 reportedAt，最后只清理自己的保留状态，不删除卷、不重启 Broker。

这是进入后端前的状态验收小步；不把未完成的 Phase 1 强行改名为完成。它不测试网络黑洞、Broker 宕机、磁盘耐久性或数据库。故障时清理是尽力完成，会报告自己的 Topic。

客户端由脚本直接观察协议回调，不解析实时调试日志。子进程退出 17 是预期故障注入，不是整个验收脚本失败；只有全流程通过，父程序才返回成功。不要把离线单元测试等同真实 Broker 验收。

报错时停在对应层，贴出完整错误与 docker compose -f infrastructure/compose.yaml logs --tail 60 mosquitto。不要贴 secrets/mqtt/clients.json。

9. 面试如何解释当前成果？

CV A：当前可以描述个人模拟设备 MQTT 链路、版本化契约和自动验证；SQL、.NET 持久化和 CI 仍属下一阶段，暂不写成已交付。

CV B：可以演示设备身份、消息顺序、Windows Python 实时消息集成和分层排障。普通 Python/.NET/Linux 调度不提供硬实时保证；当前也没有测得低延迟 SLA。

问：为什么不现在同时加 OPC UA 和 ROS 2？ 答：先验证统一数据模型与持久化边界，之后通过适配器接入新协议，避免每新增协议重新实现存储和业务逻辑。

问：Linux 容器证明你会运维 Linux 吗？ 答：它证明本项目服务在 Linux 容器中运行；宿主系统管理、systemd、补丁、SSH、防火墙与备份需要另外的实际证据。

问：QoS 1 就可靠了吗？ 答：协议确认、进入队列和数据库事务提交是不同事件。需要固定身份、幂等约束、明确确认时机与故障实验来描述端到端保证。
