Project Plan and Phase 0 Implementation Guide

Version 0.4 | 22 October 2026 | Project owner Huizi Yang

This guide records the project context, phase objectives, architecture, message contracts, Git procedures and acceptance criteria. Project context and career objectives

This independent software engineering and architecture project is inspired by Aiving Jump Tracker. It does not reproduce proprietary algorithms or internal architecture. The goal is an end-to-end system for device acquisition, communication, message processing, storage, APIs, monitoring and analytics, supporting applications for Senior Software Engineer, Systems Engineer, IoT Engineer and Software Architect roles.

The owner has more than four years of experience with C#/.NET, REST APIs, Azure, Unity, BLE, real-time applications, hardware/software integration, testing and CI/CD. At Alsensia, she worked on wearable sensor integration with real-time VR and led another engineer. Python supports simulation and analysis; .NET remains the core backend technology.

Constraints and learning approach

No sensor hardware is available. Prioritize Windows and open-source tools, with a complete local MVP that requires no paid cloud services. Keep the system modular without Kubernetes or complex microservices. Each phase includes explanation, implementation, execution, verification and failure analysis before the next phase starts.

2 Architecture and module responsibilities

Use a modular monolith. ASP.NET Core hosts both the REST API and an MQTT BackgroundService. Ingestion and query logic remain separate modules within one initial deployment unit.

Data path

Responsibility

Simulator → Mosquitto

Generate signals; publish telemetry and status

Mosquitto → MQTT Adapter

Route messages; provide topic and message metadata

Adapter → bounded queue → Processor

Separate reception from writes; validate format and identity; deduplicate

Processor → PostgreSQL

Transactional persistence and unique constraints

REST API → Query Service → PostgreSQL

Bounded, paginated device and historical queries

Backend → Prometheus → Grafana

Collect runtime metrics and display platform health

Future IMU → BLE Gateway → MQTT

Normalize hardware coordinates, units and message format

Physical hardware will replace the data source while preserving the backend MQTT contract. The simulator does not implement BLE/GATT. Pairing, fragmentation and reconnection in the future BLE Gateway require separate verification.

Why one backend process

Prioritize data boundaries, asynchronous processing, idempotency, transactions and failure semantics. Separate Worker and API deployments add operational cost. A shared process also shares resources and failure impact; split it when ingestion interferes with queries or independent scaling is necessary.

Queue capacity and backpressure

The queue must be bounded. It absorbs short bursts when the database slows down. At capacity, use an explicit waiting or controlled-rejection policy, verified together with MQTT acknowledgment behavior. An in-memory queue provides no durability guarantee. Callback completion, MQTT acknowledgment and database commit are distinct events.

Windows development topology

Initially run Python and .NET directly on Windows for debugging. Run Mosquitto, PostgreSQL and later monitoring in Docker. Host applications connect through localhost; containers use Compose service names. Containerize applications in Phase 3 while retaining host-based development. Bind the broker's published port only to loopback, require explicit authentication and keep credentials out of Git. Verify Docker prerequisites and applicable installation terms in Phase 1.

4 MQTT Message Contract

The backend subscribes to motion/v1/devices/+/telemetry and motion/v1/devices/+/status. Topics identify devices and message types. Do not split axes into separate topics or place timestamps and message IDs in topic names.

{
  "schemaVersion": 1,
  "messageId": "50aec828-b1a6-45d7-8d9a-e48b3e51ea75",
  "deviceId": "sim-001",
  "streamId": "a6e91f23-4bbc-49c0-a438-ea8f092a3b88",
  "sequence": 42,
  "sampledAt": "2026-10-21T10:00:00.123Z",
  "accelerationMps2": {
    "x": 0.03,
    "y": -0.02,
    "z": 9.81
  },
  "angularVelocityRadps": {
    "x": 0.001,
    "y": -0.002,
    "z": 0.0
  },
  "simulation": {
    "scenario": "idle"
  }
}

Each message contains one sample. messageId identifies the sample, streamId identifies a sampling run and sequence starts at zero and increases. Retries preserve the original ID, sequence and sampling time. A process restart creates a new streamId; a network reconnection alone does not require one. streamId is not a training-session ID.

Acceleration uses m/s² and includes gravity. Angular velocity uses rad/s. Use a device-local right-handed frame: X forward, Y left and Z up; rotation follows the right-hand rule. A stationary sensor with Z upward reads approximately (0, 0, 9.81). The future Gateway normalizes frames and units. Map Unity coordinates explicitly.

sampledAt is the UTC sampling time; the backend separately records receivedAt. Their difference includes device clock error and cannot be treated as network latency without clock synchronization. The optional simulation label is reference data, not evidence that an algorithm detected a jump.

Validate required fields, version, topic/payload device identity, UUIDs, nonnegative sequence numbers, UTC timestamps and finite numeric values. Unknown optional fields may be ignored. Treat physical anomalies separately from malformed messages; do not delete samples using unjustified thresholds.

5 Status storage and query interfaces

{
  "schemaVersion": 1,
  "deviceId": "sim-001",
  "connectionId": "1772e900-cc6f-433d-9ca9-d897f233030b",
  "state": "online",
  "reportedAt": "2026-10-21T10:00:00.000Z",
  "batteryPercent": 100
}

Register a retained offline Last Will before connecting. Publish retained online status after connection and send periodic heartbeats. Publish offline status before a graceful exit. A Will cannot predict the actual disconnection time, so reportedAt may be null; the backend records observation time. Generate a new connectionId per connection to support later identification of stale connection states.

Retained status may be stale. The API distinguishes the last reported connection state from activity inferred using the last received message. A retained online message is not permanent proof that a device is connected.

Table

Fields and constraints

devices

device_id primary key; first_seen_at; last_telemetry_received_at; last_status_received_at; reported_connection_state; battery_percent

sensor_readings

message_id primary key; device_id; stream_id; sequence; sampled_at; received_at; three acceleration axes; three angular velocity axes

Idempotency constraint

Unique device_id + stream_id + sequence; conflicting content is recorded, not overwritten

Historical query index

device_id + sampled_at + message_id; aligned with pagination order

REST API

GET /api/v1/devices
GET /api/v1/devices/{deviceId}
GET /api/v1/devices/{deviceId}/readings
    ?from=...&to=...&limit=...&cursor=...
GET /health/live
GET /health/ready

Limit historical queries by time range and result count. Liveness indicates that the process can respond; readiness reflects critical dependencies and ingestion state. Define dependency checks in Phase 2 so dependency failures are not automatically treated as reasons to restart the process.

10 Observations labels and detection results

The simulator knows which scenario it scheduled. The detector must infer events independently from sensor signals. A scheduled scenario is reference information; a detected event is a result that requires evaluation.

Layer

Content and purpose

Observations

Acceleration, angular velocity, timestamps and identity; detector inputs.

Reference labels

Simulator-scheduled jump intervals; debugging, evaluation and controlled supervised training.

Predictions

Independently inferred type, time interval and detector version; compared with reference labels afterward.

Incorrect and correct approaches

# Incorrect: copies the answer rather than detecting an event
if message["simulation"]["scenario"] == "jump":
    emit_event("jump")
# Correct boundary: detector receives observations only
observations = project_sensor_fields(message)
predictions = detector.detect(window(observations))
evaluation = compare(predictions, reference_intervals)

Example: the simulator schedules a jump from 10.0 to 10.8 seconds. The detector sees only the timestamped IMU window and independently reports a candidate from 10.1 to 10.7 seconds. An evaluator then matches intervals. A landing spike incorrectly reported as a jump is a false positive; reading the label to correct the prediction would invalidate the evaluation.

Keep the first version simple

In Phase 1, an optional simulation field may remain in the envelope for debugging. The detection boundary uses a separate input type and explicitly projects only observation fields. In Phase 5, store reference intervals in a separate dataset and join them after detection. No extra MQTT service is needed now. Device IDs, stream IDs and naming patterns must not implicitly encode the answer.

Validation and limits

With observations fixed, removing, shuffling or renaming labels must leave predictions unchanged. Tune rules on development data and hold out independent runs or seeds; keep overlapping windows within one split. Evaluate event-level precision, recall and timing error after defining one-to-one matching and tolerance. Scheduled labels may not perfectly match generated waveforms, so validate the generator too. Synthetic evaluation does not demonstrate real-hardware or real-jump accuracy.

Appendix Short ADRs 1 to 2

ADR 001 Software first

Status: design baseline; implementation evidence pending.

Context No hardware is available; backend learning must start now.

Decision Publish simulated IMU data directly to MQTT; preserve an adapter boundary for BLE.

Alternatives Buy hardware first; implement a virtual BLE peripheral; replay captured files.

Rationale and cost Direct MQTT is reproducible and avoids hardware dependencies. It does not exercise BLE pairing, fragmentation or radio behavior.

Revisit when Revisit after the local pipeline passes, when hardware and a concrete BLE requirement are available.

ADR 002 Modular monolith

Status: design baseline; implementation evidence pending.

Context One developer needs clear boundaries without multiple deployment pipelines.

Decision Host ingestion and REST queries in one process, separated into modules.

Alternatives Independent Worker and API services; serverless consumers.

Rationale and cost A single deployable is easier to debug and operate; ingestion and queries share resources and failure impact.

Revisit when Split when measurements show query interference, separate availability needs or independent scaling.

Appendix Short ADRs 3 to 4

ADR 003 JSON single sample

Status: design baseline; implementation evidence pending.

Context Python and .NET need a readable shared protocol at low initial rates.

Decision Use versioned JSON, one sample per message, explicit SI units and frame conventions.

Alternatives Protobuf, CBOR, binary frames or multi-sample batches.

Rationale and cost Readable messages simplify diagnosis and contract tests; repeated metadata increases bandwidth and parsing cost.

Revisit when Benchmark alternative encodings or batches if measured payload/CPU overhead limits the required rate.

ADR 004 QoS and idempotency

Status: design baseline; implementation evidence pending.

Context Retries and reconnects may deliver duplicates; storage must preserve sample identity.

Decision Start with QoS 1 and unique database identities; preserve IDs on retries and record conflicting content.

Alternatives QoS 0 for lower overhead; QoS 2; application acknowledgments with a durable sender outbox.

Rationale and cost Deduplication is explicit and testable, but acknowledgments do not prove a database commit. Metadata and uniqueness checks add cost.

Revisit when Define acceptable loss/recovery requirements in Phase 4 and test the commit-to-ack window before strengthening guarantees.

Appendix Short ADRs 5 to 6

ADR 005 PostgreSQL first

Status: design baseline; implementation evidence pending.

Context The MVP needs relational device metadata and time-filtered readings.

Decision Use ordinary PostgreSQL tables, migrations, unique constraints and a device/time index.

Alternatives Time-series extension; dedicated time-series database; object storage for raw data.

Rationale and cost One database reduces operational complexity; row-by-row high-rate storage can become expensive and requires retention planning.

Revisit when Revisit after measured write/query pressure or retention volume exceeds explicit targets.

ADR 006 Bounded memory queue

Status: design baseline; implementation evidence pending.

Context Database writes and MQTT reception can run at different rates.

Decision Use a bounded queue with explicit backpressure; choose capacity from measured rates and memory limits.

Alternatives Synchronous direct writes; unbounded queue; durable local spool or external durable log.

Rationale and cost Bounded buffering limits memory and smooths bursts; it can block reception and loses queued data on process exit.

Revisit when Consider durable buffering when outage duration or acceptable loss exceeds the tested in-memory envelope.

Appendix Short ADRs 7 to 8

ADR 007 Windows development topology

Status: design baseline; implementation evidence pending.

Context The owner debugs comfortably on Windows and needs reproducible dependencies.

Decision Run application code on the host initially and infrastructure in Compose; containerize applications in Phase 3.

Alternatives Install every service natively; develop fully inside containers or a remote environment.

Rationale and cost Host debugging remains simple and services are reproducible; hostnames differ between host and containers and Docker must be available.

Revisit when Revisit when onboarding or OS differences become costly, or the development environment cannot support Docker.

ADR 008 Sampling and reception time

Status: design baseline; implementation evidence pending.

Context Motion analysis and delivery diagnosis need different time semantics.

Decision Keep sampledAt from the producer and receivedAt from the backend in UTC.

Alternatives Reception time only; sample counters with a reconstructed timeline; synchronized device timestamps.

Rationale and cost Two timestamps preserve event timing and arrival evidence; clock skew prevents their difference from proving transport latency.

Revisit when Add explicit clock-quality/synchronization handling when real devices or accuracy targets require it.
