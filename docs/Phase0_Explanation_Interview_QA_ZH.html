1. 本阶段结论与证据

Phase 0 完成了架构、接口契约和仓库基线。Windows 已运行契约验证：Python 3.12.3、jsonschema 4.26.0，46/46 检查通过。这证明当前静态契约检查通过，不证明 MQTT 通信、数据库持久化或运动识别成功。

2. 为什么先设计，再写应用

烘焙类比：开工前先确定做哪些面包、配方单位、工序交接和验收标准。如果一个人用克，另一个人用盎司，即使每个人的动作都正确，成品仍会出错。

工程解释：Phase 0 固定问题边界、模块责任和数据语义，让模拟器与后端可以独立实现。设计是当前可修改的基线，不是预言；发现新证据后通过 ADR 调整。

3. MVP 与实施顺序

完整 MVP 的目标链路是：虚拟 IMU → MQTT Broker → 一个模块化 .NET 后端 → PostgreSQL → REST API，并增加基本日志、指标和本地部署能力。Phase 0 只完成设计和准备。

  • 初始规模：1–10 台虚拟设备，每台 10 Hz，便于观察和调试。
  • Phase 1：模拟器、Broker、验证订阅端；Phase 2：后端、数据库、API；Phase 3：完整部署与可观测性。
  • 后续再验证故障恢复、容量和分析；100–1,000 台设备是实验目标，不是当前能力。
  • 真实硬件、BLE、OTA、云部署、高可用、完整离线回放不作为第一版前置条件。

烘焙类比：先稳定做出一小盘面包，再研究同时生产一千盘。小批量成功不能直接证明大规模生产能力。

4. 模块责任与架构

模块烘焙类比责任与边界
Python 模拟器虚拟测温探头生成可重复信号和设备状态，不执行后端业务或伪装 BLE。
Mosquitto消息调度台连接、路由和协议交付，不是历史数据库。
MQTT 适配器接报窗口订阅消息、读取 Topic 身份，交给处理逻辑。
处理与持久化核验登记人员校验、去重、处理冲突、写数据库。
REST API记录查询窗口有边界的设备与历史查询。
监控与分析生产看板与复盘监控服务；后续从观测推断事件。

最初在一个 .NET 部署进程内区分适配器、应用逻辑和数据库访问。模块边界不要求进程边界；只有测得资源竞争、独立扩缩容或可用性需求，才考虑拆分服务。

6. MQTT 契约：频道与内容

Topic 像报告分类标签，Payload 像报告正文。Topic 决定消息路由，Schema 定义正文格式；Broker 不会自动理解并校验我们的业务 JSON。

  • motion/v1/devices/{deviceId}/telemetry：观测数据，计划 QoS 1、不 retained。
  • motion/v1/devices/{deviceId}/status：状态，计划 QoS 1、retained。
  • 遥测包含版本、messageId、deviceId、streamId、sequence、sampledAt、加速度和角速度；具体拼写以仓库 Schema 为准。
  • 加速度单位 m/s²，包含重力；角速度 rad/s。右手设备坐标：X 向前、Y 向左、Z 向上。静止且 Z 朝上时约 (0,0,9.81)。
  • 使用 UTC；Topic 与 Payload 的 deviceId 必须相同。

Retained 像看板上保留的最后一张状态卡，不是完整历史。旧的 online 卡可能过时，因此后端还要结合最近活动时间判断在线状态。Last Will 用于异常断线通知，不能提供未来的精确断线时间。

7. 身份、时间与顺序

messageId 像一份报告的编号；streamId 像一次采样运行的批次；sequence 是该批次内的流水号。网络重试应保留原编号、采样时间和内容，否则后端会误认为是新数据。进程重启创建新 stream；仅重连不必创建新 stream。

sampledAt 是采样时间，后端另外记录接收时间。两者之差受到时钟偏差影响，不能直接称为网络延迟。乱序到达不等于错误数据，暂时缺号也可能稍后补齐。

计划用数据库唯一约束保护 messageId 和 (deviceId, streamId, sequence)。同一身份但内容不同是冲突，应显式记录或拒绝，不能静默覆盖。

8. 设备观测与模拟标签为什么分开

烘焙类比：你把一盘面团标成“发酵完成”，这只是你的标签；检测系统必须根据体积、温度等观测独立判断，不能读标签后宣称自己识别成功。

模拟器的 jump 表示生成器安排了跳跃场景。检测器只能读取时间与 IMU 观测，自行输出事件；评估时再把预测与独立参考标签对比。固定观测后，删除或打乱标签不应改变预测。这可以检查标签泄漏。

合成数据上的正确结果验证工程流程，不证明真实花样滑冰动作识别准确率。模拟信号的简化假设应明确记录。

9. 可靠性与恢复边界

风险计划处理不能假设
重复消息稳定身份与数据库幂等约束QoS 1 不会重复
Broker 中断有界退避重连，明确缓冲策略重连后自动补齐全部历史
数据库中断有界队列、重试、背压、降级就绪状态内存队列持久可靠
进程崩溃重启，并核对确认和提交边界已接收等于已提交
坏消息拒绝、计数、受控诊断无限重试一定有帮助

收到 MQTT 确认、消息进入内存队列、数据库事务提交，是三个不同事件。必须检查实际客户端库的确认行为，再描述保证。当前不承诺端到端零丢失或 exactly-once。

11. 测试与验收：证据的层次

  1. 静态契约：合法样例接受，非法单位、类型、身份等按检查规则拒绝；已记录 46/46 通过。
  2. 运行通信：验证认证、授权、发布订阅、状态与重连；Phase 1 继续完成。
  3. 持久化：后续验证重复、冲突、数据库故障和查询边界。
  4. 故障与容量：后续记录发送与保存的身份集合、重复和缺失、延迟分布、资源使用。

每项证据写清环境、命令、预期、实际结果与限制。测试数量不是覆盖率；容器 Up 不是应用正确；设计文档不是运行结果。

12. 面试问答：为什么从模拟器开始？

回答：没有真实硬件时，我先把数据生成与传输接口分开，用可重复的模拟输入验证协议、后端和故障行为。未来通过 Gateway 保持同一业务消息契约接入设备。但模拟器不能替代真实噪声、时钟和 BLE 丢包测试。

追问：怎样证明替换容易？通过契约样例和适配器测试验证兼容，避免让核心处理逻辑依赖模拟器内部类型；不是仅画一个箭头。

13. 面试问答：为什么不用微服务或直接 REST？

回答：当前团队和规模不需要独立服务的运维成本，所以先用模块化单体。设备数据选择 MQTT，是为了练习持续遥测、连接管理和发布订阅；低频单一接收端使用 REST 也合理。选型取决于需求与代价，而不是技术排名。

14. 面试问答：QoS 1 能保证什么？

回答：它提供协议参与方之间的至少一次交付语义，可能重复；实际断线行为还受会话和持久化配置影响。它不能证明后端数据库已经提交。我计划使用稳定消息身份、数据库约束和故障注入验证端到端行为，目前不宣称零丢失。

15. 面试问答：如何解释幂等和乱序？

回答：同一消息重试保持身份，重复处理不应增加业务记录；同一身份不同内容作为冲突处理。采样顺序与到达顺序分开记录，允许有效迟到数据，缺号先视为待确认的缺口。

16. 面试问答：设备增加一百倍怎么做？

回答：先估算设备数 × 采样频率 × 消息大小，并计入消费者转发和数据库索引成本；再测试瓶颈。考虑批量发送、批量写入、保留策略、分区或拆分摄取服务。不能从十台设备的成功推断一千台也满足延迟和恢复目标。
