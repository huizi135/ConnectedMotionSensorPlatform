为什么先做离线信号？

烘焙类比：先检查温度探头读数是否合理，再检查报告能否送到调度台。如果一开始同时加入探头、网络和数据库，异常时难以判断是哪一层出错。

本步拆出不依赖网络的生成逻辑。输入是设备、采样流、开始时间、样本数量、频率和随机种子；输出是符合现有契约的 JSON。MQTT 传输在下一个小步接入。

IMU 的静止读数

IMU 是惯性测量单元，这里模拟三轴加速度计和三轴陀螺仪。固定设备坐标：X 向前、Y 向左、Z 向上。静止、Z 向上的示例，加速度约 (0,0,9.81) m/s²，角速度约 (0,0,0) rad/s。加速度计包含重力对应的静止响应，因此静止不意味着三个轴都为零。

每轴添加小幅有界随机噪声：加速度 ±0.03 m/s²，角速度 ±0.003 rad/s。它只是教学数据，不是任何真实 IMU 的校准噪声模型。本步不模拟方向变化、跳跃或着地。

操作 1：运行测试

git pull --ff-only
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_idle_signal.py" -v

用途：在连接网络前验证信号生成。预期：Ran 5 tests，OK。本项目已装 jsonschema，无新增依赖。若出现 ModuleNotFoundError: jsonschema，先确认使用项目 .venv；必要时执行 .\.venv\Scripts\python.exe -m pip install -r tools/requirements-contracts.txt。

操作 2：生成三个样本

.\.venv\Scripts\python.exe -m simulator --samples 3 --seed 42

预期：三行 JSON 和一条 PASS offline idle 汇总。stdout 只输出 JSON，汇总写 stderr；终端显示顺序可能交错。sequence 是 0、1、2；相邻 sampledAt 相差 0.1 秒；Z 加速度接近 9.81，角速度接近零。

默认 10 Hz 表示每秒十个逻辑采样时刻，不表示程序每 0.1 秒暂停一次。离线生成立即输出，尚不承担实时调度。未来实时发布使用单调时钟安排节奏，采样时间仍记录为 UTC。

为什么相同 seed 的两次输出不完全相同？

seed 控制信号噪声。每次 CLI 运行自动创建新的 streamId 和当前开始时间，因此身份和时间变化是预期行为。固定 seed、streamId、开始时间及全部参数，生成的完整消息才可重复；测试验证了这一点。UUID5 将采样流、设备和序号映射为稳定 messageId；重试必须复用原样本，不能重新采样。不要复用同一采样流身份来表示不同内容。

为什么没有 idle 标签？

当前输出仅含观测，省略可选 simulation 字段。我们知道运行的是 idle 生成器，但这不是后端识别结果。后续加入场景参考数据时与检测输入隔离，独立评估，不用标签代替识别。

测试、故障与工程边界

五项测试覆盖：固定输入可重复；身份/序号/UTC 时间；静止重力与噪声范围；全部样本符合现有 Schema；无效设备 ID、数量、频率和时区拒绝。助手环境已通过，Windows 待验收。测试并不证明物理真实性、运动识别准确率或网络可靠性。

无效参数会明确报错；无需重启 Broker。这个离线程序既不读取密码，也不依赖 Docker 是否运行。若命令找不到 simulator，应先确认位于仓库根目录，且更新到了当前分支。

面试问答

问：为什么把生成器与 MQTT 分开？ 答：让信号逻辑能在无网络环境下确定性测试，缩小故障范围，并让同一生成器可用于离线分析和在线发布。

问：为什么静止加速度不是零？ 答：当前契约采用包含重力静止响应的加速度计读数，Z 向上时约 9.81。去除重力得到线性运动加速度需要额外定义与处理，不能混用。

问：固定随机种子保证一切可重复吗？ 答：不保证。还要控制时间、身份、配置和随机状态。本项目将确定性定义为固定所有生成输入，而不是仅固定 seed。

问：10 Hz 是经过论证的动作识别频率吗？ 答：不是，是调试起点。真实需求需结合动作频率、传感器能力和误差目标验证。
